# Gherkin + Autonomous TDD Integration

**Date**: 2025-11-05
**Status**: Design Phase
**Purpose**: Enable Autonomous TDD Agent to build features from Gherkin acceptance tests

---

## Overview

The Autonomous TDD Agent can be extended to accept **Gherkin acceptance tests** as high-level specifications, automatically breaking them down into incremental unit tests and building the implementation using strict TDD discipline.

**Workflow:**
```
Human writes Gherkin → Agent plans unit tests → Agent builds incrementally → Acceptance tests verify
```

---

## Architecture: Two-Level Testing

```
┌─────────────────────────────────────────────────────────────┐
│ Level 1: ACCEPTANCE TESTS (Gherkin)                        │
│ ─────────────────────────────────────────────────────────── │
│ • Written by humans/product owners                          │
│ • Describes WHAT the system should do                       │
│ • Business-level verification                               │
│ • Defines "DONE" - when scenarios pass, feature complete    │
└────────────────┬────────────────────────────────────────────┘
                 │
                 │ drives implementation
                 ▼
┌─────────────────────────────────────────────────────────────┐
│ Level 2: UNIT TESTS (TDD)                                   │
│ ─────────────────────────────────────────────────────────── │
│ • Generated by Autonomous TDD Agent                         │
│ • Describes HOW the system works internally                 │
│ • Component-level verification                              │
│ • Builds incrementally until acceptance tests pass          │
└─────────────────────────────────────────────────────────────┘
```

### Separation of Concerns

| Aspect | Gherkin (Acceptance) | Unit Tests (TDD) |
|--------|---------------------|------------------|
| **Author** | Human (Product/Business) | Agent (Autonomous) |
| **Language** | Natural language (Given/When/Then) | Python/pytest |
| **Scope** | Feature/scenario (macro) | Function/class (micro) |
| **Purpose** | Verify business requirements | Verify implementation details |
| **Changes** | Rarely (stable requirements) | Often (refactoring, optimization) |
| **Audience** | Non-technical stakeholders | Developers/maintainers |

## Implementation Design

### Extended Agent Class

```python
class AutonomousTDDAgent:
    """Autonomous TDD agent with Gherkin support."""

    def __init__(self, ensemble_learner: EnsembleLearner, test_runner: TestRunner):
        self.ensemble = ensemble_learner
        self.test_runner = test_runner
        self.gherkin_parser = GherkinParser()  # New component

    def build_feature(self,
                     requirement: str = None,
                     gherkin_file: Path = None,
                     max_iterations: int = 50) -> TDDResult:
        """Build feature from requirement text OR Gherkin file.

        Args:
            requirement: Natural language requirement (original approach)
            gherkin_file: Path to .feature file (Gherkin approach)
            max_iterations: Maximum TDD cycles before stopping

        Returns:
            TDDResult with tests, code, and playbook updates
        """
        if gherkin_file:
            return self.build_from_gherkin(gherkin_file, max_iterations)
        elif requirement:
            return self.build_from_requirement(requirement, max_iterations)
        else:
            raise ValueError("Must provide requirement or gherkin_file")

    def build_from_gherkin(self, gherkin_file: Path, max_iterations: int = 50) -> TDDResult:
        """Build feature from Gherkin acceptance tests.

        Process:
        1. Parse Gherkin file
        2. Extract requirements from scenarios
        3. Plan unit test increments (ensemble-based)
        4. Execute TDD cycles
        5. After each cycle, check if acceptance tests pass
        6. Stop when all scenarios pass or max_iterations reached

        Args:
            gherkin_file: Path to .feature file
            max_iterations: Stop after this many cycles (safety limit)

        Returns:
            TDDResult with complete implementation
        """
        # 1. Parse Gherkin
        feature = self.gherkin_parser.parse(gherkin_file)
        logger.info(f"Parsed feature: {feature.name}")
        logger.info(f"Scenarios: {len(feature.scenarios)}")

        # 2. Extract requirements
        requirements = self._extract_requirements_from_gherkin(feature)
        logger.info(f"Requirements extracted: {requirements.summary()}")

        # 3. Plan unit test increments (ensemble voting)
        test_plan = self._plan_increments_from_gherkin(requirements)
        logger.info(f"Test plan created: {len(test_plan)} increments")

        # 4. Execute TDD cycles
        results = []
        for i, increment in enumerate(test_plan):
            if i >= max_iterations:
                logger.warning(f"Reached max_iterations ({max_iterations}), stopping")
                break

            # Execute RED → GREEN → REFACTOR → LEARN
            cycle_result = self._tdd_cycle(increment)
            results.append(cycle_result)

            # Check if acceptance tests pass yet
            acceptance_result = self._run_acceptance_tests(gherkin_file)
            logger.info(f"Acceptance: {acceptance_result.passed}/{acceptance_result.total} scenarios passing")

            if acceptance_result.all_passed:
                logger.info("🎉 All acceptance tests passing! Feature complete.")
                break

        # 5. Final validation (must pass all scenarios)
        final_acceptance = self._run_acceptance_tests(gherkin_file)
        if not final_acceptance.all_passed:
            raise TDDFailure(
                f"Feature incomplete: {final_acceptance.failed}/{final_acceptance.total} scenarios failing"
            )

        return TDDResult(
            tests=self._collect_test_files(),
            code=self._collect_source_files(),
            playbook_updates=self._collect_learned_bullets(),
            acceptance_tests_passed=True,
            cycles_executed=len(results)
        )
```

### Gherkin Requirements Extraction

```python
def _extract_requirements_from_gherkin(self, feature: GherkinFeature) -> GherkinRequirements:
    """Extract structured requirements from Gherkin feature.

    Uses ensemble to identify:
    - Domain objects needed (User, Email, Password, etc.)
    - Validation rules (email format, password strength)
    - API endpoints (POST /register, GET /login)
    - Business logic (hashing, authentication)
    - Error handling (validation errors, error messages)

    Args:
        feature: Parsed Gherkin feature

    Returns:
        GherkinRequirements with structured breakdown
    """
    # Each model analyzes the feature
    analyses = {}
    for model_id, llm_client in self.ensemble.clients.items():
        prompt = f"""Analyze this Gherkin feature and extract technical requirements.

Feature: {feature.name}
{feature.description}

Scenarios:
{self._format_scenarios(feature.scenarios)}

**Task**: Identify the technical components needed:

1. **Domain Objects**: What entities/models are needed? (User, Order, Product, etc.)
2. **Value Objects**: What validated types are needed? (Email, Password, Money, etc.)
3. **Validation Rules**: What constraints must be enforced? (format, length, range, etc.)
4. **Business Logic**: What operations are required? (calculate, transform, verify, etc.)
5. **API Endpoints**: What HTTP routes are needed? (POST /register, GET /users/:id, etc.)
6. **Error Handling**: What error messages should be returned? (validation errors, not found, etc.)
7. **Data Persistence**: What needs to be stored? (database models, repositories, etc.)

Provide structured analysis in JSON format."""

        response = llm_client.chat(prompt)
        analyses[model_id] = self._parse_requirements_json(response)

    # Ensemble votes on requirements
    consensus_requirements = self._vote_on_requirements(analyses)

    return GherkinRequirements(
        feature=feature,
        domain_objects=consensus_requirements.domain_objects,
        validation_rules=consensus_requirements.validation_rules,
        api_endpoints=consensus_requirements.api_endpoints,
        business_logic=consensus_requirements.business_logic,
        error_handling=consensus_requirements.error_handling
    )
```

### Unit Test Increment Planning

```python
def _plan_increments_from_gherkin(self, requirements: GherkinRequirements) -> list[TestIncrement]:
    """Plan unit test sequence from Gherkin requirements.

    Uses ensemble to determine optimal order:
    1. Domain models (foundation)
    2. Value objects (validated types)
    3. Business logic (operations)
    4. API layer (endpoints)
    5. Integration (full scenarios)

    Args:
        requirements: Structured requirements from Gherkin

    Returns:
        Ordered list of unit test increments
    """
    # Each model proposes unit test breakdown
    proposals = {}
    for model_id, llm_client in self.ensemble.clients.items():
        prompt = f"""Plan unit tests to implement this Gherkin feature incrementally.

Feature: {requirements.feature.name}

Requirements:
{requirements.format_for_prompt()}

**Task**: Break down each scenario into incremental unit tests.

**Guidelines**:
1. Start with domain models (entities, value objects)
2. Add validation rules (format, constraints)
3. Add business logic (calculations, transformations)
4. Add API layer (endpoints, serialization)
5. Each test should be small and focused
6. Order tests by dependency (can't test API before model exists)
7. Cover happy path first, then error cases

**Example**:
Scenario: User can register with email
→ test_user_model_can_be_created
→ test_user_requires_email
→ test_email_validation_accepts_valid_format
→ test_email_validation_rejects_invalid_format
→ test_user_requires_password
→ test_password_is_hashed
→ test_registration_endpoint_exists
→ test_registration_creates_user
→ test_registration_returns_success_message

**Output Format**:
Provide ordered list of test names with brief description of what each tests.
"""

        response = llm_client.chat(prompt)
        proposals[model_id] = self._parse_test_sequence(response)

    # Ensemble votes on best sequence
    consensus_sequence = self._vote_on_test_sequence(proposals)

    # Convert to TestIncrement objects
    increments = []
    for test_spec in consensus_sequence:
        increments.append(TestIncrement(
            test_name=test_spec.name,
            description=test_spec.description,
            dependencies=test_spec.dependencies,
            scenario_index=test_spec.scenario_index
        ))

    return increments
```

### Acceptance Test Runner

```python
def _run_acceptance_tests(self, gherkin_file: Path) -> AcceptanceTestResult:
    """Run Gherkin acceptance tests using behave or pytest-bdd.

    Args:
        gherkin_file: Path to .feature file

    Returns:
        AcceptanceTestResult with pass/fail for each scenario
    """
    # Run acceptance tests (using behave framework)
    result = subprocess.run(
        ["behave", str(gherkin_file), "--format", "json"],
        capture_output=True,
        text=True,
        timeout=60
    )

    # Parse results
    output = json.loads(result.stdout)

    scenarios_passed = 0
    scenarios_failed = 0
    scenario_results = []

    for feature in output:
        for scenario in feature["elements"]:
            if scenario["status"] == "passed":
                scenarios_passed += 1
            else:
                scenarios_failed += 1

            scenario_results.append(ScenarioResult(
                name=scenario["name"],
                status=scenario["status"],
                steps=[step["status"] for step in scenario["steps"]],
                error=scenario.get("error_message")
            ))

    return AcceptanceTestResult(
        total=scenarios_passed + scenarios_failed,
        passed=scenarios_passed,
        failed=scenarios_failed,
        all_passed=(scenarios_failed == 0),
        scenario_results=scenario_results
    )
```

## Integration with Step Definitions

The agent needs to create **step definitions** (glue code) that connect Gherkin steps to actual code.

### Auto-Generated Step Definitions

```python
# Generated by agent: features/steps/registration_steps.py

from behave import given, when, then
from src.models.user import User
from src.api.registration import RegistrationAPI

@given('I am on the registration page')
def step_impl(context):
    context.api = RegistrationAPI()
    context.response = None

@when('I enter email "{email}"')
def step_impl(context, email):
    context.email = email

@when('I enter password "{password}"')
def step_impl(context, password):
    context.password = password

@when('I click "Register"')
def step_impl(context):
    context.response = context.api.register(
        email=context.email,
        password=context.password
    )

@then('I should see "{message}"')
def step_impl(context, message):
    assert message in context.response.message

@then('I should see error "{error_message}"')
def step_impl(context, error_message):
    assert context.response.error == error_message

@then('my password should be hashed in database')
def step_impl(context):
    user = User.get_by_email(context.email)
    assert user.password != context.password  # Not plaintext
    assert user.password.startswith("$2b$")  # bcrypt hash
```

**Agent generates these step definitions during Cycle 6-8** (API layer implementation).

## Benefits of Gherkin Integration

### 1. Clear Success Criteria
- **Gherkin defines "DONE"**: When all scenarios pass, feature is complete
- No ambiguity about what to build
- Product owner can verify completion

### 2. Business-Readable Specification
- **Non-technical stakeholders write Gherkin** (product owners, BAs, customers)
- **Agent builds implementation** (technical work automated)
- Gap between business and technical is bridged

### 3. Two-Level Verification
```
Unit tests (micro) → Ensure components work in isolation
Acceptance tests (macro) → Ensure feature works end-to-end
```

Both must pass for feature to be complete.

### 4. Living Documentation
- Gherkin scenarios serve as **up-to-date documentation**
- Unlike written docs, these are **verified by tests**
- If scenario passes, documentation is accurate

### 5. Incremental Complexity
```
Scenario 1: Happy path → Agent builds basic implementation
Scenario 2: Validation error → Agent adds validation rules
Scenario 3: Edge case → Agent hardens error handling
```

Each scenario adds complexity in manageable increments.

### 6. Regression Prevention
- All existing scenarios must pass before new work
- Agent learns: "Don't break existing acceptance tests"
- Playbook accumulates patterns: "When adding validation, preserve happy path"

## Technical Challenges & Solutions

### Challenge 1: Step Definition Generation

**Problem**: Agent must create glue code connecting Gherkin to implementation.

**Solution**:
- Generate step definitions during API layer cycles (cycles 6-10)
- Use ensemble to vote on step definition patterns
- Learn common patterns in playbook ("Given I am logged in" → setup auth context)

### Challenge 2: Test Data Management

**Problem**: Gherkin scenarios need consistent test data.

**Solution**:
- Use `@given` steps to set up test fixtures
- Agent creates `conftest.py` with fixtures
- Reset database between scenarios (using `@before_scenario` hook)

**Example**:
```python
# Generated by agent: features/environment.py

def before_scenario(context, scenario):
    """Reset database before each scenario."""
    context.db = TestDatabase()
    context.db.reset()

def after_scenario(context, scenario):
    """Clean up after scenario."""
    context.db.close()
```

### Challenge 3: Acceptance Test Failures

**Problem**: Agent doesn't know WHY acceptance test failed (only sees FAILED status).

**Solution**:
- Parse behave output for step-level failures
- Identify which step failed (Given/When/Then)
- Use failure info to guide next TDD cycle

**Example**:
```
Acceptance test failed:
  Scenario: Successful registration
    ✓ Given I am on the registration page
    ✓ When I enter email "alice@example.com"
    ✓ When I enter password "SecurePass123"
    ✓ When I click "Register"
    ✗ Then my password should be hashed in database
        AssertionError: Password is stored in plaintext

Agent interprets: Need to add password hashing
Next TDD cycle: test_password_is_hashed_on_creation
```

### Challenge 4: Over-Implementation

**Problem**: Agent might add features not required by Gherkin.

**Solution**:
- Strict adherence to "YAGNI" (You Aren't Gonna Need It)
- Only implement what's needed for current scenario
- Ensemble reviews: "Does this code help any Gherkin scenario pass?"

### Challenge 5: Complex Scenarios

**Problem**: Some scenarios require many steps (20+ unit tests).

**Solution**:
- Break complex scenarios into sub-scenarios
- Use "Background" section for common setup
- Agent can suggest splitting scenarios

**Example**:

## Integration with Existing Components

### With Test Review Agent
```python
# Before learning from TDD cycle, validate test quality
cycle_result = self._tdd_cycle(increment)

# Review test quality (substance over style)
review_result = self.test_reviewer.review_test_file(cycle_result.test_file)

if review_result.overall_score < 0.7:
    logger.warning(f"Test quality low: {review_result.overall_score:.0%}")
    logger.warning("Issues: " + ", ".join(issue.message for issue in review_result.issues))
    # Don't learn from low-quality tests
    return

# Ensemble learns from high-quality test
self.ensemble.learn_from_cycle(cycle_result)
```

### With Ensemble Learner
```python
# After each TDD cycle, ensemble votes on patterns
def _ensemble_learn(self, test_code: str, impl_code: str, result: TestResult):
    """Ensemble extracts and votes on patterns from TDD cycle."""

    # Each model proposes patterns
    proposals = []
    for model_id, llm_client in self.ensemble.clients.items():
        bullets = self._extract_patterns(test_code, impl_code, llm_client)
        proposals.extend(bullets)

    # Cross-voting on all proposals
    approved_bullets = self.ensemble.vote_on_bullets(proposals)

    # Add to playbook
    self.playbook.add_bullets(approved_bullets)
```

### With Deliberative Discussion
```python
# When voting is contested (40-60%), trigger deliberation
if bullet.is_contested(0.4, 0.6):
    logger.info(f"Bullet contested ({bullet.approval_rate:.0%}), starting deliberation")

    # Models discuss bullet with reasoning
    self.ensemble.conduct_deliberation([bullet])

    # Final vote after discussion
    if bullet.is_approved():
        self.playbook.add_bullet(bullet)
```
